Accounts & Sign-in

Stealth & Anti-detection

Many sites actively block browser automation—at best a challenge or CAPTCHA, at worst an outright account ban. Tools like Playwright or Puppeteer with a stealth plugin patch a blank browser into impersonating a human, and every patch is a crack for the anti-bot systems to find. chrome-use's answer is different: it doesn't simulate a human—it IS your real, already-logged-in browser.

Why anti-detection is a core capability

For any agent running against real sites, the first hurdle isn't "can it click a button," it's can it avoid being flagged as a bot. Anti-bot vendors like Akamai, PerimeterX, DataDome, and Cloudflare look at both the fingerprint (does the browser show automation traces) and the behavior (how the mouse moves, how text is typed). Once triggered, the cost is often more than a single failed request—it's this account getting flagged and banned.

So chrome-use treats anti-detection as a first-class capability, not an afterthought patch. The core idea in one line: prefer driving your real, already-logged-in Chrome—what the site sees is a genuine human browser. Only for the cases that truly need an isolated browser do we fall back to the "native overrides > JS lies" approach to keep the traces clean.

Core philosophy: 0% stealth = change nothing

When connected to your real Chrome (via the extension relay), the number of JavaScript patches chrome-use injects is zero. Your browser's fingerprint is completely real. The guiding principle is "native CDP/Chrome overrides over JS lies"—a redefined getter is itself detectable, while a native override is not.

  • navigator.webdriver = false is done via Emulation.setAutomationOverride (native, so lie-detectors like CreepJS can't catch it).
  • Runtime.enable is off by default. An active Runtime domain is a detectable CDP signal (the "runtime leak" that patchright/rebrowser talk about)—even when connected to your real Chrome. It's only enabled when you actively turn on console/error capture; click, fill, eval, etc. work fine without it.
  • Nothing is written into the page's DOM to find elements. snapshot, find, nth, pick and auth login hold the elements they chose by node handle, never by a temporary marker attribute, which a page's MutationObserver would see written and removed. State a command keeps in the page (a click watch, a key receipt, an upload buffer) is likewise held by handle, never put on window or under a Symbol.for key.
✅ Why 0% is the strongest score
On CreepJS, 0% stealth is the key number: because the connection path changes nothing, the lie-detector has no "override" to catch at all. It isn't "the patches are well made," it's there are no patches at all—this is the real browser's own score.

When some dashboards read navigator.languages order or IP geolocation, they may raise a soft navigator / location flag—that reflects your real Chrome's language list and network, not an automation trace.
Headed launches preserve the native fingerprint
Headed --launch no longer replaces CPU, GPU, UA Client Hints, screen or iframe properties with JavaScript. Pages and workers use Chrome's real values. Explicit headless launches remain detectable through workers; stealth status warns about this limitation. Basic probes do not guarantee Cloudflare clearance or account safety. Chrome may also mark CDP IME compositionend events untrusted.

Three lines of defense

In chrome-use, anti-detection is three layers stacked: from "which browser to use" to "what the fingerprint looks like" to "how human the behavior is."

① Real session > headed > headless (disabled)

Anti-detection ranking: real, already-logged-in Chrome (extension connection) > headed launched browser > headless (disabled). A genuine human browser has no headless / automation cracks at all, so any anti-bot-sensitive task should prefer it. Headless is disabled by default—it is itself a bot crack (--headed is the stealth default and always on).

bash · headed by default 
# --headed is the stealth default, always on —— headless is disabled
# (it's a bot crack: creepjs reports ~33% for headless, 0% for headed)
# only unlock it on a headless server with no display:
$ AGENT_BROWSER_ALLOW_HEADLESS=1 chrome-use --launch open "https://example.com"

② Native fingerprint overrides

For isolated / launched browsers, use native overrides to align key fingerprints to the identity you want—none of them are JS lies, so lie-detectors can't catch them. These switches only apply to --launch:

On macOS, launched Chrome also disables MacAppCodeSignClone. A short-lived automation browser does not need Chrome's in-place-update clone, and disabling it prevents killed sessions from leaving APFS clones that consume real disk after later Chrome updates.

bash · fingerprint overrides (--launch) 
# native timezone override (IANA id, or "auto" to derive from locale), Intl+Date follow, no JS lies
$ AGENT_BROWSER_TIMEZONE="Asia/Tokyo" chrome-use --launch open "https://example.com"

# hide the local IP via WebRTC (when a proxy is set, force through it so the real IP never leaks)
$ AGENT_BROWSER_BLOCK_WEBRTC=1 chrome-use --launch open "https://example.com"

# session-stable canvas/audio fingerprint noise (off by default, because noise is itself a kind of "lie")
$ AGENT_BROWSER_HIDE_CANVAS=1 chrome-use --launch open "https://example.com"
ℹ️ webdriver is a native override too
navigator.webdriver = false goes through Emulation.setAutomationOverride—a native implementation, not a redefined getter, so lie-detectors like CreepJS can't catch it.

③ Behavior layer: --humanize beats Akamai/PerimeterX/DataDome

A clean fingerprint isn't everything—the strongest anti-bot vendors also score behavior. A click that teleports the cursor to the dead center of an element with zero press delay is a crack, even though our CDP events are isTrusted. With humanize on, the cursor moves like a hand: a click lands along a curved, decelerating Bézier trajectory on a jittered point inside the element (never dead center); typing uses variable keystroke intervals; scrolling eases in segments; drags follow a curve.

It's adaptive—each navigation probes for known anti-bot vendors (cookies / scripts / globals), and guarded pages auto-upgrade to full human motion. Every other page gets fast (since 1.5.255): a short curved path, landing jitter, key presses for type and wheel scrolling, at a small cost in speed. Sites that run their own bot checks the vendor probe cannot see (Douyin, Xiaohongshu, Bilibili, X, Weibo, Kuaishou, Zhihu, Taobao, JD, YouTube and others) always get human.

bash · humanize 
# off (instant) | fast (default: lightweight eased trajectory) | human (full curve + landing jitter + typing rhythm + eased scroll/drag)
$ chrome-use --humanize human click "@ref=e42"

# or set the default for the whole session via an env var
$ AGENT_BROWSER_HUMANIZE=human chrome-use type "hello"
✅ Leave it on auto
The default is fast; the adaptive detector raises pages guarded by Akamai/PerimeterX/DataDome, and the high-risk sites above, to human. Use off only where nothing watches and speed matters (local test pages, internal tools).

Cloudflare: pass once, reuse the clearance

Passing a Cloudflare challenge once mints a cf_clearance cookie (HttpOnly—invisible to eval/document.cookie, read it with chrome-use cookies). It's bound to your IP + User-Agent: reuse the same egress IP and UA to skip the challenge until it expires. Driving the user's real Chrome (relay) persists it natively; for an isolated session, use --session-name <name> to save / restore.

Before spending effort on solving it, run chrome-use cf-status (aliases cf, clearance) as a preflight— to avoid re-solving a challenge that's already passed.

bash · cf-status 
# preflight: is the page currently a Cloudflare challenge? is there already a valid cf_clearance?
$ chrome-use cf-status

# read the HttpOnly cf_clearance cookie
$ chrome-use cookies
ℹ️ The three recommendations cf-status gives
proceed (already through, don't re-solve), solve (challenge present, no clearance), reissue (has clearance but the page is still blocked → IP/UA drifted, re-solve). Treat it as a preflight, don't re-solve a challenge that's already passed.

Stealth mode switch (extension options)

Session-scoped internal DOM reads require an isolated execution context. If creation, recreation or node resolution cannot keep that context, the command returns isolation_unavailable rather than retrying in the page world. Failed isolated-context setup is cached for one second; a later read retries setup without reloading the page or falling back to the main world. Wait for navigation to settle and observe again; some same-process frame operations may remain unsupported. User-requested evaluation, site adapters, deliberate editor-model access and explicitly supplied contexts keep their existing semantics. The existing AGENT_BROWSER_MAIN_WORLD=1 compatibility override disables this default isolation requirement; it is not a stealth-preserving workaround. This policy is independent of the extension cursor setting.

The extension's options page has a Stealth mode switch, on by default. While it is on, chrome-use adds nothing of its own to the pages it drives: no overlay, no named page globals, and site adapters' clicks and typing go through args.ui as real input events. Features that draw into pages only work with it off; today that is the agent cursor (a soft cursor and click ripple), whose switch is greyed out until stealth mode is turned off. Inspect & Ask works either way, since you start it yourself.

Turning stealth mode on or the agent cursor off also removes existing cursor overlays, click ripples and window.__abCursor, after any in-flight draw. Cleanup uses current debugger connections and verifies removal. If a tab is detached or unreachable, settings warns that cleanup is unconfirmed: reload affected pages before relying on stealth. Cleanup retries on normal reattachment; changing the setting does not force a connection.

ℹ️ For contributors
A new feature that the page could see (a DOM node, a global, a listener, a synthetic event, a fixed timing) must stay off while stealth mode is on. Pull requests and releases are checked for it; see "Stealth first" in AGENTS.md.

Self-check: chrome-use stealth status

You can inspect the current stealth state at any time: chrome-use stealth status reports the current mode plus a set of live probes (webdriver / chrome / plugins / UA), along with the current configuration. Add --json for machine-readable output. The headless, scope and warnings fields explain the limits; a known headless launch does not report all checks passing.

bash · stealth status 
# stealth self-check: mode + live probes (webdriver / chrome / plugins / UA) + overrides in effect
$ chrome-use stealth status
$ chrome-use stealth status --json

Prompt injection

A page can hide instructions for agents where a person never sees them: off-screen, opacity:0, clipped to 1px, or the same colour as the background. snapshot, get text and read used to print that text exactly like visible text, so an agent could not tell them apart. Three defaults now apply:

  • Hidden text is left out. snapshot, get text and read (active tab) drop text a person can't see and end with a note saying how much; --include-hidden keeps it. The check is a read in the isolated world: no DOM writes, no cloned nodes, no requests, so stealth mode is unaffected.
  • MCP and panel output is marked untrusted. chrome-use mcp fences every browser tool result with a nonce and a line saying it is page content, not instructions from the user; --no-content-boundaries turns it off. The CLI default is unchanged so piped output stays the page's bytes; use --content-boundaries there.
  • Panel pre-exec check. When a shell command an agent wants to run carries a URL or snippet that a page showed and the user did not type (a page's curl … | sh, say), the approval card says so in red and the command is never approved automatically, full access or not. Limit: only backends that ask before running a command can be stopped. Pi never asks; Claude in full access runs with bypassPermissions and Codex in full access with approvalPolicy: never, so their commands never reach the panel.
