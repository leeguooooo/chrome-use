What Agents Can Do

Site Adapters

A site adapter is a small per-site script that calls the site's own API from your signed-in tab. On popular sites like GitHub, Reddit and Bilibili the agent gets clean data in one command instead of clicking page by page, and publishing adapters post an article or upload a video in one command too.

Ask your agent

List the last 30 open issues and PRs in this repo.

The github/issues adapter returns them as JSON in one call.

What new videos are in my Bilibili following feed?

Feeds that need sign-in are read as you.

Publish post.md to CSDN with the title Hello.

The body is read from the file, and the command returns once publishing finishes.

I check this site every day. Write an adapter for it.

Next time the same job is one command.

What the agent does

  1. When the agent lands on a site that has adapters, chrome-use prints which ones exist for that domain, and the agent uses the command it names.
  2. It checks the arguments with site info, then runs site <name>/<cmd> --json, which navigates to the site by itself.
  3. Publishing adapters read the body from a file and take local video paths directly; --until-done keeps going until the upload and publish finish.
  4. If you use a site a lot and it has no adapter, chrome-use prompts the agent to ask whether you want one. If you agree, it writes the adapter into ~/.chrome-use/my-sites/ and registers it.

What you'll see

  • Your tabs stay as they are: the agent opens background tabs in a ✦ <project> tab group in your Chrome and does not take focus. Click over whenever you want to watch.
  • Requests go out from your signed-in tab, as your account. If the site is signed out the command fails with a login wall, and the agent passes the choice (sign in this time, always, or never) to you; it does not choose for you.
  • When a third-party OpenCLI command runs, the output says it is not maintained by chrome-use. Posting, deleting, liking and following on your real account should not rely on OpenCLI.
  • A publish that returns timeout has not necessarily failed; the run in the page may still finish. The agent should check the page before rerunning, and you can click over to that tab yourself, so nothing gets posted twice.
  • At the end the agent runs done: tabs it opened along the way close, and pages you need to see or keep using stay open.

To read "structured data from site X," the cheapest path is to skip snapshot + click. Before you open, page through, and click your way across GitHub / Reddit / Bilibili, check whether a ready-made site adapter exists — a small community-written JS snippet that hits the site's own JSON API directly from your logged-in tab and hands you clean structured data in one shot. No clicking, no scraping, no screenshots.

For task-specific CLI guidance, load chrome-use skills get core/site-adapters. Ordinary clicks and form actions are already covered by core.

What it is

A site adapter is a community-written JS function: it calls the site's own JSON API directly from your currently logged-in tab and returns clean, structured data. Essentially it's a packaged, per-site eval — except you don't have to write it yourself, and you don't have to reverse-engineer each site's endpoints.

Because it runs inside the tab you're already logged into and makes requests as you, feeds that require a session — like bilibili/feed or twitter/… — read fine too. That's exactly what hand-crafting URLs or anonymous scraping can't do.

ℹ️ Relationship to eval
If you already know how to use eval to hit a site's internal API, a site adapter is that same code distilled into a command — maintained by the community and organized per site. You skip the grunt work once, and everyone else gets to reuse it.

How to use it

Four actions: pull the sources once (update), see what's installed (list), see how a given adapter is called (info), and run it (site <name>/<cmd>).

bash 
$ chrome-use site update                            # one-time: pull community, official, and extra sources
$ chrome-use site list                              # what's installed (github/issues, reddit/search…)
$ chrome-use site info github/issues                # an adapter's params + which domain it runs on
$ chrome-use site info github                       # every adapter in the pack, with params + usage
$ chrome-use site github/issues owner/repo --json   # run → JSON (navigates there for you)
  • site update: pulls adapters from the bb-sites community source, the chrome-use-sites official source, and any configured extras. Only needed once; after that chrome-use keeps them in sync automatically (see "Auto-triggering" below).
  • site list: lists every <name>/<cmd> installed locally, e.g. github/issues, reddit/search.
  • site info <name>/<cmd>: shows which params an adapter declares and which domain it runs on — check this before calling, and you'll know what to pass.
  • site info <name>: the same for every adapter in one pack, each with a usage line showing its required args.
  • site <name>/<cmd> [args] --json: actually runs it. Add --json for one line of parseable structured output.
  • If the current URL cannot be read, site_domain_unverified stops domain navigation and OpenCLI fallback. A URL-read timeout does not establish that the tab is on the wrong site. Check get url and snapshot before trying again.

With --json, that last command returns the site's own data, already cleaned into a parseable structure (excerpted and indented below):

✅ info first, then run
When you're not sure what params an adapter needs, run site info <name>/<cmd> first to see its declared params and target domain, then pass them accordingly. Cheaper than blindly running once and reading the error.

Params and navigation

Adapter params are filled positionally in declaration order; to override one by name, use --key value. The two forms mix freely: positional args fill the slots, and --key pins a specific override.

positional vs --key override 
# positional args fill in declaration order
$ chrome-use site github/issues owner/repo --json

# --key overrides by name (order doesn't matter)
$ chrome-use site reddit/search --query "chrome-use" --sort new --json

When it runs, it navigates to the domain the adapter declares — and if your current tab is already on that domain, it reuses the current tab instead of opening a new one. The request still happens inside the tab you're logged into, so signed-in feeds like bilibili/feed or twitter/… return normally (why they do is covered under "What it is" above).

ℹ️ It navigates for you
You don't have to open the target site manually first. site <name>/<cmd> navigates to the adapter's domain and then executes; but you do need to be already logged in to that site for logged-in feeds to be readable.

Long text, local files, long runs

Adapters that write (publish an article, upload a video) also run as one command: the body is read from a file, a local file is handed to the adapter, and waiting for an upload or a publish is no longer bound by the ~8s budget of a single command.

publish adapters 
# Long text from a file or stdin, instead of "$(cat post.md)"
$ chrome-use site csdn/article-publish --title "Hello" --markdown @post.md
$ cat post.md | chrome-use site csdn/article-publish --title "Hello" --markdown @-

# An arg the adapter declares as "type": "file" takes a local path (shown by site info)
$ chrome-use site douyin-creator/video-publish --video ./clip.mp4 --title "Hello"

# Keep going until the upload / publish is really done
$ chrome-use site bilibili-creator/video-publish --title "Hello" --tags a,b --until-done --timeout 10m

# Writing an adapter: declare the file arg in @meta.args; optional "timeout": 600 (seconds) in @meta
#   "video": {"required": true, "type": "file", "input": "input[type=file]"}
# In the function: put the file on the page's file input, report progress, read the time this run has
#   await args.video.setOn();   args.progress('uploading');   args.budgetMs
  • --key @path reads the value from a file, --key @- from stdin, and --key-file path is the same thing spelled out. @name that is not a file stays literal (--user @jack); @x.md or @dir/x that looks like a path but does not exist is an error, so a typo is never posted as text. For a literal value starting with @, write --key \@text.
  • A "type": "file" arg takes a local path. The adapter puts it on the page's file input itself with args.video.setOn(), so there is no separate upload step and no selector to know. The page can only name the selector, never the path.
  • An adapter runs in the background of the page and chrome-use polls it, so the ~8s budget of one relay command does not apply. --timeout <300|90s|10m> sets the total time; the default is the adapter's @meta.timeout, else 120s.
  • --until-done: when the adapter returns status: "incomplete" / "uploading", or a page navigation ended the run, it is rerun until it finishes or the timeout passes (default 600s). Without the flag that status is returned as is, and you rerun the same command.
  • Progress the adapter reports with args.progress(...) is printed to stderr, and returned as progress in --json along with attempts and elapsedMs.
  • Write adapters (publish, delete, comment, follow) can have chrome-use do their input with args.ui (1.5.253+): args.ui.click(el), hover, type(el, text, {clear}), press('Enter'), scroll(el | pixels). It sends real CDP input (isTrusted: true) with a curved pointer path and varied key timing, wheels the element into view first and lands inside it, and fails with a reason when the element is gone, has no size or is covered. An adapter's own el.click() / dispatchEvent is isTrusted: false, which a site can see.
  • With "world": "isolated" in @meta (1.5.259+) the adapter runs in the tab's isolated world: same DOM, cookies and storage, its own JS, so nothing the page wrapped (querySelector, fetch, ...) is ever called. What only page JS has (a React fiber or other element expando, an app store, the page's own signed fetch) comes through args.page(fn, ...args): fn is sent by its source and run in the main world with the JSON args, and its JSON result comes back; it cannot see the adapter's variables and takes a selector, not an element. Older chrome-use ignores the key and runs in the main world: const page = args.page || ((fn, ...a) => fn(...a)).
⚠️ A timeout is not a failure
status: "timeout" only means the adapter was still running when time ran out; the run in the page may finish afterwards. Check the page before rerunning a publish command, so nothing is published twice.

Auto-triggering — see it, use it

You don't have to remember which sites have adapters. chrome-use keeps the adapter sources in sync automatically (on first use + weekly), and whenever you reach a page whose domain has adapters it tells you: on every open / navigate / snapshot, and on any other command that lands you on a different site (tab new, switching tabs, back / forward, a click that navigates, the first command on a tab you didn't open). Staying on one site, you hear about it once. The hint is:

  • a line on stderr: site adapters for <domain>;
  • a siteAdapters: {domain, commands} field in --json output.
auto-hint · stderr 
$ chrome-use open https://github.com/epiral/bb-sites
# … as the page opens, a line pops up on stderr:
site adapters for github.com — prefer these for structured data:
   github/issues, github/pulls, github/repo …
   e.g. chrome-use site github/issues <repo> --json
   args: chrome-use site info github
✅ See the hint, prefer the site <name>/<cmd> it lists
When you see site adapters for <domain>, don't snapshot + click to read the data — just use the site <name>/<cmd> it names: cheaper, more reliable, and already installed. You also don't need to run site update yourself first — just use the command it gives you.

A site you use a lot has no adapter

When you drive the same site a lot (30+ actions this session, or on 3+ days) and no adapter covers it, chrome-use adds siteAdapterSuggestion: {domain, actionsThisSession, daysUsed, message} to one response (stderr: site adapter suggestion: …), so the AI asks you whether to turn the steps it keeps repeating into an adapter. It comes once per site per session and not again for two weeks; local hosts and IPs are skipped. If you say yes, the AI writes it to ~/.chrome-use/my-sites/<name>/<cmd>.js, registers the folder once with chrome-use site add ~/.chrome-use/my-sites, and runs site update. AGENT_BROWSER_SITES_NO_SUGGEST=1 turns it off.

Adding OpenCLI-format adapters

site add detects OpenCLI-format sources: an OpenCLI plugin repo (e.g. chrome-use site add darinouyang/opencli-plugin-shipxy), a zip, or a local dir such as your existing ~/.opencli/clis. Their commands run through the same OpenCLI runtime over your chrome-use session and show as (opencli: <source>) in site list. .js modules are supported, and .ts ones on Node 22.13+; YAML-only plugins are not (OpenCLI itself stopped loading YAML in 1.8). OpenCLI adapters are Node code running on your computer with your user's permissions, not inside the page like chrome-use adapters. So a local dir is added directly, while a remote source is pinned to the commit (zip: SHA-256) you trusted: at a terminal site add lists its modules and asks, and scripts or agents must pass --trust-node-code. site update re-copies local dirs but never moves a remote pin; run site add again to take a newer version. On a shared name: our adapters, then your OpenCLI sources, then the OpenCLI package.

OpenCLI is a last resort

With Node.js 20+ on PATH, site update also installs OpenCLI (about 180 sites and 1,300 commands; a pinned version, installed with --ignore-scripts). A name/cmd that neither adapter pack has runs through OpenCLI's own runtime, driving your current chrome-use session and its logins, e.g. chrome-use site hackernews/best --limit 5 --json. They show as (opencli) in site list, site info shows their args, and they come last in the site hint. On a shared name ours always win (priority: a site add source, then the official chrome-use-sites pack, then the bb-sites community pack, then OpenCLI); if ours fails and OpenCLI has a read command of the same name, that runs instead (writes never retry). AGENT_BROWSER_SITES_NO_OPENCLI=1 turns them off. douyin/delete, douyin/update, twitter/delete, twitter/like, twitter/follow, bilibili/user-videos and bilibili/creator-stats used to come from OpenCLI and are now maintained in chrome-use-sites (ported with attribution, Apache-2.0); OpenCLI never runs them, and a cache that predates them is synced on first use. Delete, like and follow open their page first, so run them with --until-done. OpenCLI is third-party code chrome-use does not maintain, and its commands have shipped broken. Every OpenCLI run prints a stderr note: … third-party OpenCLI command, not maintained by chrome-use; --json adds maintainedBy: "opencli", readOnly and notice. Use our own adapter whenever one exists; for posting, liking, following, deleting or publishing on your real accounts, don't rely on OpenCLI: port the command into chrome-use-sites.

When the site is not signed in

An adapter that finds the site signed out returns {"loginRequired": true} (with any error code, plus an optional loginUrl, the sign-in page relative to the site). error: "login_required" or "not_logged_in" means the same. chrome-use also counts a failed run as signed out when one of the adapter's fetch calls got HTTP 401 or was redirected to a sign-in page, or the tab ended on one. Then the command fails with a login wall: <host> is not signed in … line on stderr and loginWall in --json, pointing at auth login --bwu instead of the adapter's own message. The first time for a site it asks whether to sign in from the vault: this time, always for that site, or never. A terminal gets a prompt; an agent gets loginWall.ask with the question and one command per answer, and must relay it to you rather than choose. With chrome-use auth autologin always <host> it opens loginUrl, signs in with the vault login for the site and runs the command once more. auth autologin status shows the decisions and auth autologin off <host> forgets one. A write adapter is rerun only when it reported the login itself; one whose failure was inferred from a 401 or redirect may have half-run, so it is left for you to check.

Writing your own: analyze and verify

Do the action that loads the data on the page first (search, scroll, open the list), then run chrome-use site analyze. It lists the API calls the page made, the state it embeds (__NEXT_DATA__, __INITIAL_STATE__, …) and any anti-bot vendor, and recommends a data source. In order of preference: a public API, the site's own JSON API called from the page with its cookies, embedded page state, then the DOM. Each step down breaks more often. Once it works, chrome-use site verify <name>/<cmd> [args] --write-fixture records the shape of a good result; later, site verify fails (exit 1) when a field disappears, changes type, or a list comes back empty. The fixture keeps the shape only, never values.

ℹ️ Exception on a fresh environment
Only on a brand-new environment where the adapter sources haven't been pulled yet might naming a site <name>/<cmd> report "not installed." In that case run site update once and re-run the command.

Record an adapter by doing the flow

For a write flow (fill a form, check out, post), you can skip writing the adapter: do it once by hand after chrome-use teach start, then chrome-use teach stop --adapter writes a skeleton to ~/.chrome-use/my-sites/<site>/<flow>.js that replays it through args.ui. See Teach by Demonstration.

When to use it vs extract --schema vs snapshot

There's often more than one path to the same page of data. Site adapters are the first choice for structured data from a known site; fall back down the ladder when no suitable adapter exists. The table below helps you pick.

Your situationUseWhy
Structured data from a known site (GitHub issues, Reddit/HN search, Bilibili / Twitter feeds), especially once logged in chrome-use site <name>/<cmd> Hits the site's JSON API directly, runs as you, skips snapshot + click — cheapest and most reliable
Structured data from any page with no community adapter — tables, search results, feed rows, dashboards extract --schema '{rows,fields}' Give it a shape, get clean JSON in one call — no writing eval, no dumping the whole page's HTML
You need to reason over it with a model, or need @refs to interact snapshot -i --json A structured snapshot with stable refs — readable and drives follow-up click / type
A one-off extraction needing a custom shape with special logic eval --stdin Write JS directly in the page's MAIN world — most flexible (an adapter is just this, distilled)
ℹ️ Cheapest to most expensive
Roughly: site adapter → extract --schema → snapshot/eval loop. If there's an adapter, use it; no adapter but a regular shape, use extract --schema; only when neither fits fall back to the usual manual snapshot / eval loop. For the full picture of data extraction, see Extracting Data.

Source and license

Adapters come from two defaults: the bb-sites community source and the chrome-use-sites official source. chrome-use fetches and executes them at runtime — this repo does not bundle or redistribute any adapter code, and site update fetches the latest version from upstream each time.

ℹ️ Fetched at runtime, not built in
Because adapters are maintained in the community and official sources and fetched only at runtime, the command set you see changes as either default source updates; site list reflects the version you synced to locally this time.

FFmpeg extracts the explicitly requested local frame before browser interaction, retains a new PNG without overwriting, and hands it to the adapter's normal verified image-upload path. Missing frames fail. Near-black/nearly uniform frames return cover_frame_review_required; review the saved file and choose another timestamp, or explicitly use --allow-dark-cover true with a new output path.
